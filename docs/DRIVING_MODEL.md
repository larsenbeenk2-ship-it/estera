# Worldwide routes and driving simulation

The planner accepts valid coordinates worldwide, including cross-border tracks and the antimeridian. Submitted address, place, neighborhood, and postal-code search uses Nominatim without a country filter. Lightweight real-place suggestions use Photon, a separate OpenStreetMap search-as-you-type service; road and path availability still depends on OpenStreetMap coverage and the configured routing provider.

## Place API

`POST /api/search` accepts `{query: string}` (2–200 characters) and returns `{places: Place[], attribution: string}`. `Place` is `{name, label, latitude, longitude, zoom?, bounds?}`; optional zoom frames address and region results at an appropriate scale. Search results may include `bounds: [west, south, east, north]`, converted from Nominatim's `[south, north, west, east]` bounding box so a client can fit the full result area. Bounds are included only when all four values are finite, within longitude/latitude ranges, and ordered with positive width and height; malformed or degenerate bounds are omitted. Nominatim search is explicit, not autocomplete; include a city or country to disambiguate an address or postal code. The frontend resolves explicit telephone area-code queries such as `area code 415` through a bundled NANPA geographic-code snapshot before submitting a labeled regional search. Most codes resolve only to their state/province/country; results disclose that precision. Bare three-digit inputs remain general place/postal searches. The snapshot source, date, and update script are in `web/src/data/`.

`POST /api/suggest` accepts `{query: string}` (3–200 characters) and returns up to five real worldwide `Place` matches from Photon. The browser waits 150 ms after a non-composing text edit before calling it and cancels stale work. Up to 20 exact queries are reused for five minutes in page memory, so repeated searches and backspacing can display instantly; nothing is written to local storage or the backend cache. Submitting search keeps matching suggestions usable until the detailed results arrive. Photon receives the typed query; its endpoint is configurable with `OPENLOCATION_AUTOCOMPLETE_URL` and defaults to `https://photon.komoot.io/api/`. The submitted-search endpoint remains available when suggestions are unavailable. Photon is used only for short, single-user suggestion requests; Nominatim is never queried for type-ahead.

`POST /api/reverse` accepts `{latitude: number, longitude: number}` and returns a flat `Place` without `bounds`. Its coordinates are exactly the requested coordinates. Its label describes the nearest suitable indexed object, which may be on a neighboring street; it never snaps a selected map point to the geocoder's returned centroid. No address produces `address_not_found`. Provider failures remain structured errors, so the UI can retain the selected coordinate. `OPENLOCATION_REVERSE_URL` overrides the endpoint; otherwise it is the `reverse` sibling of `OPENLOCATION_SEARCH_URL`.

All place endpoints require the existing loopback host, same origin, and application token. None creates a device session, writes to a phone, or persists a route. Submitted search and reverse retain their shared lock and 1.05-second spacing policy; Photon suggestions have separate 250 ms spacing and a five-second timeout. A newer suggestion request cancels the previous worker before acquiring its slot, so obsolete text cannot hold up the latest query. Provider 429 responses remain errors without automatic retries. This is a bounded single-user use of [Photon's search-as-you-type API](https://github.com/komoot/photon#demo-server); the public provider's network latency and availability remain outside the app's control. Strict coordinate ranges, finite-number validation, device authorization, session ownership, and storage revisions still apply to all locations.

## Route contract

### Adaptive driving update

The existing authenticated route/preview/start requests accept two additional optional settings: `driving_speed_mode: "adaptive" | "manual"` (default `adaptive`) and `stop_policy: "mapped" | "all"` (default `mapped`). They apply to constant-timing driving only; walking, cycling and recorded GPX timing retain their behavior. No new device command, identity rule, storage transaction or background job is introduced. The same pure timeline supplies preview and playback. A live explicit speed command selects manual pacing and preserves position.

Adaptive cruising uses known segment limits minus 2 mph (0.89408 m/s), with small smooth variation below the limit. Missing limits use provider estimates bounded by conservative road-class cruise ceilings. Local/unknown roads no longer inherit an unrestricted faster provider estimate. These ceilings are simulation assumptions, not inferred legal limits. Stops and acceleration lower the whole-trip average further. Unknown map values are never treated as posted limits.

Intersections add `control: "stop_sign" | "traffic_signal" | "uncontrolled" | "unknown"` (default `unknown`). Only mapped stop signs/signals cause automatic stops under the default policy. Unknown junctions, bends, and side entrances alone do not. Explicit user waypoints still stop. `traffic_controls_source` reports `provider`, `partial`, `unavailable`, or `none`. Control enrichment uses bounded, cached same-provider requests; failure leaves the road route usable with unknown controls and visible incomplete coverage. Retries of route planning have no phone side effects.

The following fields are optional on input. Old saved driving routes now use adaptive pace and mapped-only stops unless explicitly set to manual/all; routes need recalculation to obtain missing map controls.

| Field | Default | Meaning |
| --- | --- | --- |
| `driving_speed_mode` | `"adaptive"` | Known limits minus about 2 mph; `"manual"` uses selected cruise speed. Only constant-timing driving is affected. |
| `stop_policy` | `"mapped"` | Stop only at mapped controls; `"all"` is an explicit legacy option for all junction candidates with an added wait. |
| `traffic_controls_source` | `"none"` | `"provider"`, `"partial"`, `"unavailable"`, or `"none"` describes successful control matching, not guaranteed real-world coverage. |
| `segment_speeds_mps` | `[]` | A provider-derived or fallback pace for each consecutive point pair. When supplied, length must be `points.length - 1`; every entry is a finite number from 0.01–100. |
| `segment_speed_limits_mps` | `[]` | Same length rule; entries are finite numbers from 0.01–100 or `null` for an unknown/unlimited limit. Only known provider limits are populated. |
| `speed_source` | `"none"` | `"provider"`, `"mixed"`, `"fallback"`, or `"none"`, describing timing provenance. Provider timing is an estimate. |
| `segment_road_classes` | `[]` | One classification per geometry pair: motorway, trunk, primary, secondary, tertiary, unclassified, residential, service_other, ramp, or unknown. Supports conservative missing-limit pacing and curve behavior. |
| `segment_grades` | `[]` | One finite slope ratio from −1 to 1, or `null`, per geometry pair. `0.05` means an estimated 5% uphill grade; missing elevation remains `null`. |
| `terrain_source` | `"none"` | `provider`, `partial`, `unavailable`, or `none`; describes available route grade coverage. Driving does not request terrain data. |
| `realistic_motion` | `false` | Enables acceleration and braking in manual driving mode. Adaptive driving always uses these. New driving directions use `true`. |
| `intersections` | `[]` | Unique interior `{point_index, name?, control?}` junction candidates, separate from user stops. Missing control means `unknown`. |
| `intersection_source` | `"none"` | `"topology"`, `"maneuvers"`, or `"none"`; incomplete data remains labeled accordingly. |
| `intersection_pause_seconds` | `0` | 0–60 seconds at selected controls. New driving directions use 3. Zero removes dwell, but adaptive motion still comes to a full halt at mapped controls. |
| `speed_variation` | `0` | Deterministic spatial variation from 0–0.5. New driving directions use 0.06. Adaptive amplitude is capped at 1.7 mph to keep the cruise centered below the limit. |

Recorded timing rejects road speed arrays, realistic motion, variation, and automatic junction pauses; original timestamps remain a separate timing mode. Explicit waypoint dwells retain their behavior. A shared waypoint/junction uses the greater dwell, not their sum. Reversal remaps points, stop indices, and estimated speed arrays but clears directional driving limits and control classifications. Recalculate to obtain a road-legal return route with fresh metadata.

Adaptive driving ignores `speed_mps` and uses each road's limit or bounded estimated pace automatically. Manual driving uses `speed_mps` as the cruise target; variation and known limits still apply. With known grades, walking/cycling use the selected flat-ground pace and apply terrain once, avoiding double-counting hills already embedded in a provider ETA. Missing grades retain the existing provider profile scaling relative to base paces (1.4 and 4.2 m/s). Driving is unaffected by grade. Recorded tracks retain their timestamps even if informational grades are present.

## Provider routing and pacing

All travel modes request Valhalla's full polyline6 road/path geometry and OSRM maneuver output. Driving uses `auto` costing with `shortest: false` and `use_distance: 0`, favoring practical travel time while retaining access and turn restrictions. Walking uses `pedestrian`; cycling uses `bicycle` with a city bicycle and a comfortable 15.12 km/h base speed. These are mode-appropriate provider routes; there is no straight-line fallback for unavailable driving roads. Walking access between a driving stop's road anchor and exact pin can use estimated connectors or a direct walking fallback as described below.

The request includes `shape_attributes.time`, `shape_attributes.speed`, and `shape_attributes.speed_limit`. Where supported, OSRM annotations give segment seconds, meters per second, and known speed limits. Limits in km/h or mph are converted to m/s. If annotations are absent, maneuver distance divided by duration supplies a segment pace. Missing timing uses the mode's base pace and is marked as fallback. Native Valhalla responses retain their maneuver-timing fallback; optional native shape speeds and limits are in km/h and converted to m/s. Estimated pace caps are 2.2 m/s walking, 9 m/s cycling, and 38.9 m/s driving. Adaptive driving with a known limit uses that limit minus the margin instead of these estimates.

After routing, the same provider's `trace_attributes` endpoint enriches the original geometry with `shape_match: "edge_walk"`. Metadata is accepted only when the returned polyline6 coordinates have the same count and order as the requested route and edge spans are valid, ordered, and nonoverlapping. It never rematches to a nearby road or replaces the route geometry. `edge.speed_limit` is converted from km/h to m/s; unknown and unlimited values remain unknown. When both route annotations and edge data supply a limit, the lower value is retained. Classification comes from the matched directed edge, including ramp use.

For walking and cycling, `edge.weighted_grade` supplies an edge-level, quantized percentage estimate, converted to the stored slope ratio. Both maximum-grade availability fields must be valid: Valhalla's missing-elevation sentinel is not treated as flat ground. This is terrain metadata, not a survey or a point-by-point elevation measurement. Only the existing routing provider receives the route geometry. Enrichment uses its existing rate limit and cache, at most four requests/50,000 points, and an eight-second total budget. Unsupported responses, timeout, missing data, and provider failures leave the route usable with unknown attributes; cancellation still cancels planning. There are no retries, new credentials, authentication changes, or phone writes during enrichment.

Existing saved routes need recalculation for fresh limits, classifications, and hills. New fields are optional and require no storage migration. Walking connectors preserve matched road metadata and have unknown grades of their own. Reversing a raw track reverses road classes and reverses/negates the estimated slopes; directional driving limits and controls are still cleared.

Junction candidates use connected cross-way topology where available. At least three bearings plus incoming/outgoing edges identify a crossing; indices and coordinates must agree with the geometry. Two-bearing nodes are also eligible for control lookup, without being presumed intersections. Explicitly classified motorway junctions are excluded. Native or partial topology responses use explicit turn/roundabout maneuvers and remain labeled as partial coverage.

Valhalla's OSRM directions expose limits but omit stop-sign flags. Driving therefore enriches route nodes using the configured provider's sibling `/locate` endpoint with `verbose: true`. A control is accepted only when the oriented incoming edge ends at that route node and its preceding geometry agrees with the route at about 5 and 20 meters. Signals on the matching end-node ID are also accepted. Stop signs belonging to a side road or opposite approach cannot be assigned by proximity alone. Ambiguous or missing controls stay unknown. This reads mapped stop/signals, not live red/green phases: every mapped signal currently receives a modeled halt and selected wait.

## Playback and preview

One backend `Timeline` drives both preview and phone playback. Adaptive driving starts and ends at rest, stops at explicit waypoints and mapped controls, and slows for bends. Forward acceleration and backward braking passes enforce reachable speed caps, including braking before lower speed limits. Each driving segment is divided into acceleration, cruise, and braking phases as needed, using 1.6 m/s² acceleration and 1.6 m/s² braking for earlier slowing. Smooth manual and adaptive driving both evaluate bends with 25-, 60-, and 120-meter geometry windows. Sub-meter centerline noise is ignored; nodes and segment midpoints both receive curve caps, so speed stays down through the bend instead of surging between vertices. Broad motorway/trunk curves allow 2 m/s² estimated lateral acceleration, ramps 1.5, and other roads 1.1. A separate sharp-corner bound retains slow right-angle turns. These are simulation assumptions, not vehicle measurements.

For unknown speed limits, road-class cruise ceilings are 55 mph motorway, 45 trunk, 35 primary, 30 secondary, 25 tertiary/unclassified/residential/ramp/unknown, and 15 service. The cruise target is the lower of the provider estimate and the ceiling minus 2 mph, with bounded variation. None of these estimates is reported as a mapped limit. Supplied limits cap both adaptive and manual driving. Preview legs and live samples expose `speed_limit_mps`, `road_class`, and `grade`; the playback dock shows the mapped limit or explicitly identifies a missing limit.

### Hill response

For positive slope ratio `g`, cycling pace scales by `max(0.15, 1 / (1 + 14g))`; walking uses `max(0.3, 1 / (1 + 4g))`. A 5% climb therefore gives about 59% of selected cycling pace and 83% of selected walking pace before acceleration transitions. Descending pace increases at most 35% for cycling and 10% for walking. These are bounded simulation heuristics, not a rider-specific power model. Grade transitions use acceleration/braking limits of 0.45/0.6 m/s² for cycling and 0.2/0.25 for walking. Unknown grade retains provider pacing; an entire connected active-travel section with any known grade uses smooth transitions to avoid speed jumps at coverage boundaries. Explicit pauses still reach rest. Cars never apply the grade multiplier.

### Walking to stops and stop duration

Directions stops accept `walk_to_stop: boolean` (default `true`) beside `dwell_seconds` (0–86400). Driving directions preserve the exact selected pin and its roadside anchor. Every drive starts in the car at the provider's road start, without an origin walking leg. The origin's `walk_to_stop` preference is retained for recalculation when stops are reversed but does not add walking at departure. Enabled destination stops more than 0.5 meters from the anchor request mapped pedestrian directions. An intermediate stop requests roadside → pin → roadside in one itinerary, obtaining both walking directions; the final stop ends at its pin. Destination pauses begin at the pin after the incoming walk. Disabled destination stops retain road-only arrival.

Walking requests reuse the configured Valhalla provider, cancellation, cache, and rate limiter. They use the provider's [pedestrian costing model](https://valhalla.github.io/valhalla/api/route/api-reference/#pedestrian-costing-options), with one request per enabled off-road stop and a 45-second budget for all access directions. Usable mapped walking routes are retained, with estimated straight connectors between their endpoints and the roadside anchor or exact pin. There is no 30-meter endpoint-gap restriction. When the provider returns `no_route` for pedestrian directions, the walking portion uses an estimated direct road-to-pin path, with a return walk at intermediate stops. Cancellation, timeout, unavailable or busy providers, and malformed route geometry remain failures. Estimated portions render as faint dots; mapped walking paths render as gold dashes. Estimates do not establish that a path is physically walkable. The combined route retains the 500 km and 50,000-point bounds. No device write or authentication change is introduced.

Geometry is assembled before final route validation. Explicitly stationary provider legs are accepted only with zero length/time and real coincident geometry, allowing separate destinations to share one roadside point. Such stops keep distinct waypoint indices; zero-distance driving links do not produce spurious car entry/exit transitions.

`segment_modes` is optional and either empty or one entry per geometry pair. Mixed routes require constant-timing driving and accept only driving/walking segments. Waypoints preserve `requested_coordinate`, `walk_to_stop`, and optional `access`: `roadside_coordinate`, roadside `arrival_index`/`departure_index`, nullable `walking_to`/`walking_back` ranges (`start_index`/`end_index`), and `estimated_segments` (global geometry-pair indices). New driving routes set `walking_access_version: 1`. Older saved routes retain their geometry and display a recalculation notice, including version 1 routes with an origin `walking_back` range. Reversal remaps indices and swaps outbound/return walking ranges with geometry.

Walking runs at 1.4 m/s independently of driving pace and road speed limits. Driving brakes to rest before mode changes; three-second `exit_car` and `enter_car` transitions show parking and entry. Preview legs and live samples expose `phase`, `stop_index`, and nullable `parked_coordinate`, alongside `travel_mode` and `transition`. Phases include `driving`, `parking`, `walking_to_stop`, `paused_at_stop`, `walking_back`, and `entering_car`. Live samples also expose `pause_remaining_seconds`. Speed changes preserve distance and elapsed pause/transition time. The map reconstructs separate parked-car and moving-person markers directly from playback state, including after seeking and at the final destination.

The sidebar exposes a large pause duration beside the walking switch at destination stops. The origin instead explains that driving starts in the car on the road. The hours/minutes/seconds picker uses native scroll snapping, click selection, keyboard navigation, and numeric entry; 24 hours forces minutes and seconds to zero. Zero duration adds no wait. Preview and live playback show the stop name and prominent pause countdown. Walking failures and older route notices provide a direct recalculation action.

Smooth driving and terrain-aware active travel subdivide long segments at approximately 40 meters, keeping curve and hill transitions consistent on sparse geometry. For exceptionally long imported tracks, spacing grows to bound additional subdivisions at about 50,000. These internal motion points do not alter stored route geometry or stop indices.

Preview legs add nullable `start_speed_mps` and `end_speed_mps`. When both exist, distance after `t` seconds is `v0*t + 0.5*((v1-v0)/duration)*t*t`; divide by leg distance to interpolate along that leg. Legacy legs retain linear time interpolation. `Timeline.sample()` also supplies instantaneous `speed_mps`, including zero at stops and completion. Live pace changes preserve traveled distance or elapsed dwell even when acceleration phases change.

The provider's `road_seconds` remains distinct from the simulation duration. Acceleration, conservative pace caps, and simulated stops can make playback take longer than the provider estimate. Preview starts at normal elapsed time; visual preview acceleration is a UI choice and must not change the route's stored timing.

## Bounds and evidence

The road/terrain intelligence update passed one focused offline command: `pytest -q tests/test_route_metadata.py tests/test_motion_intelligence.py tests/test_stop_access.py` — 56 tests in 0.26 seconds. It covers exact-route metadata matching, units, missing elevation, enrichment limits and failures, conservative missing-limit pace, lower-limit braking, hill effects and downhill bounds, broad/tight/noisy bends, reverse tracks, recorded timestamps, and live stop/walk continuity. The IPC schema was regenerated. No live map-provider request, browser, frontend build, or phone playback was run. Rebuild/restart and recalculate saved routes to use the update; mapped limits and coarse grade estimates remain dependent on provider data.

Online routing retains its 500 km itinerary/resolved-route cap, 25 stops, batches of ten locations, 50,000 geometry points, 8 MiB provider-response limit, bounded cache, single-flight locks, request spacing, 30/35-second timeouts, and HTTPS/loopback policy. Cancellation is checked around each provider request. Invalid or disconnected geometry and misaligned annotations reject the result. There are no automatic retries. Optional road/terrain enrichment has its separate eight-second total budget above.

Control lookup is limited to 120 route nodes, ten per batch, within a total 12-second budget. It shares the directions cache/rate limit and response cap. Long routes, unsupported `/locate`, malformed responses, rate limits, and missing map data can yield partial or unavailable controls. Existing route geometry and speeds remain usable. Walking and cycling make no control requests. Additional route nodes are sent only to the already-configured routing provider.

The adaptive update passed one focused offline command: 13 tests in 0.19 seconds. Cases cover the cruise average and fluctuation on sparse geometry, braking before lower limits, acceleration bounds, mapped-only stops including zero added wait, speed-change continuity, directional control matching, provider failure/cancellation, route-to-timeline integration, native speed units, reversal, and recorded timing. The IPC schema was regenerated. No browser, live provider, phone, app restart, or frontend build was run; UI source changes require the next frontend build and backend restart to appear in the running app. Existing saved routes need recalculation for new metadata.
